IS 295a · System Blueprint

Software Requirements Specification (SRS)

A section-by-section guide to specifying the information system you will build — what it must do, who will use it, the data it manages, the rules and interfaces it must respect, and the quality it must achieve.

Prepared by: Dr. Reinald Adrian Pugoy — First Semester, AY 2026–2027
01 · Overview

What the SRS Is

The Software Requirements Specification (SRS) forms part of the IS 295a System Blueprint. It translates the findings of the requirements analysis into a structured specification of the information system to be developed.

The SRS defines:

  1. What the system must do.
  2. Who will use it.
  3. The data it must manage.
  4. The rules and constraints governing its operation.
  5. Its required interfaces.
  6. The quality requirements it must satisfy.

The requirements baseline

The SRS serves as the requirements baseline for system design, development, testing, and evaluation.

Requirements should therefore be:

Clear· Specific· Consistent· Feasible· Verifiable
02 · Overview

Role of the SRS in IS 295

The SRS is a component of the IS 295a System Blueprint. It represents the requirements of the information system to be developed and provides the requirements baseline for the succeeding stages of the project.

The overall progression is:

Needs Assessment→ Requirements Analysis→ SRS→ System Design→ Approved System Blueprint→ Development→ Testing and Evaluation→ Final System

IS 295a vs. IS 295b

IS 295a
  • The SRS is prepared as part of the System Blueprint.
IS 295b
  • The SRS is not submitted as a separate deliverable. IS 295b proceeds from the approved System Blueprint to system development, testing, and evaluation.
03 · The Nine Sections

Section 1. Introduction

This section provides an overview of the system and establishes the scope of the SRS.

1.1 Purpose

State the purpose of the SRS and identify the information system being specified. Briefly explain:

  • what system the document covers;
  • what the SRS is intended to specify; and
  • how the SRS will guide the development of the system.

1.2 System Overview

Provide a concise description of the information system. Identify:

  • the problem or operational need addressed by the system;
  • the general purpose of the system;
  • its intended users; and
  • its major capabilities.
Keep it concise. This should provide only enough context to understand the requirements. It should not repeat the detailed discussion in the manuscript.

1.3 Scope

Define the boundaries of the system. Specify:

Within scopeOutside scope
Major functions included in the systemImportant functions or processes outside the scope
Processes supported by the system
Users or organizational units covered
Guiding question — What will the system cover, and what will it not cover?

Section 2. Overall Description

This section describes the general context in which the system is expected to operate.

2.1 Product Perspective

Explain how the proposed system fits within the existing organizational and technological environment. Describe, where applicable:

  • existing processes or systems that it will replace, improve, or complement;
  • its relationship with other systems; and
  • external services or platforms on which it will depend.
System context diagram — A system context diagram may be included to show the system boundary and its interaction with users and external systems.

2.2 User Classes and Characteristics

Identify the major types of users who will interact with the system. For each user class, describe:

Role· Responsibilities· System access or permissions· Characteristics affecting system use

Example:

User ClassDescriptionMajor Access/Responsibilities
AdministratorManages the systemUser management, configuration, reports
StaffPerforms operational processesCreate, review, and update records
End UserAccesses system servicesSubmit requests and track status

2.3 Constraints, Assumptions, and Dependencies

Identify conditions that may affect the design, development, or operation of the system. These may include:

  • institutional policies;
  • legal or regulatory requirements;
  • required technologies or platforms;
  • existing infrastructure;
  • organizational procedures;
  • third-party systems or services; and
  • assumptions regarding users, data, or operating conditions.
Remember — Include only those relevant to the proposed system.

Section 3. Functional Requirements

This section specifies what the system must do and constitutes the core of the SRS.

Functional Requirements (FRs) define the specific capabilities, behaviors, or services that the system must provide. They are written from the system's perspective. Organize the requirements according to major modules, features, or business functions.

Each functional requirement should:

  1. Have a unique identifier.
  2. Describe a specific system behavior or capability.
  3. Be clear and unambiguous.
  4. Be feasible within the project scope.
  5. Be testable or verifiable.

3.1 [Module or Feature Name]

Briefly describe the module or feature, then list its requirements. Example:

FR-001 — The system shall allow registered users to authenticate using their email address and password.
FR-002 — The system shall validate all required fields before accepting an application.
FR-003 — The system shall generate a unique reference number for each successfully submitted application.

Avoid vague statements such as "The system should be user-friendly." Requirements should describe behaviors or capabilities that can later be verified.

Functional Requirements vs. Use Cases

Functional Requirements (FRs) and Use Cases (UCs) are related, but they serve different purposes.

Two different questions

Functional Requirements
  • Describe what the system must do.
Use Cases
  • Describe how an actor interacts with the system to accomplish a goal.
AspectFunctional Requirement (FR)Use Case (UC)
Main questionWhat must the system do?How does an actor accomplish a goal using the system?
PerspectiveSystemActor interacting with the system
FocusSpecific capability or behaviorGoal-oriented interaction or workflow
Typical form"The system shall..."Sequence of actor-system interactions
ScopeUsually one specific requirementMay involve several functional requirements
ExampleFR-014: The system shall generate a unique reference number for each submitted application.UC-03: Submit Application

One use case, several requirements

For example, the use case UC-03: Submit Application may involve several functional requirements:

FR-010 — The system shall allow an applicant to create a new application.
FR-011 — The system shall validate all required application fields before submission.
FR-012 — The system shall allow the applicant to upload required supporting documents.
FR-013 — The system shall record the date and time of submission.
FR-014 — The system shall generate a unique reference number for each successfully submitted application.
FR-015 — The system shall display a confirmation after successful submission.

Thus:

UC-03: Submit Application→ FR-010FR-011FR-012 FR-013FR-014FR-015
Don't simply rewrite one as the other. Students should not simply rewrite a use case as a functional requirement, or vice versa. A single use case may involve several functional requirements, while a functional requirement may support one or more use cases.

Section 4. Use Cases

This section describes how actors interact with the system to accomplish specific goals.

Whereas Functional Requirements specify individual system capabilities, Use Cases organize those capabilities into meaningful interactions between actors and the system.

4.1 Use Case Diagram

Provide a use case diagram showing:

  • system boundary;
  • actors;
  • major use cases; and
  • relevant relationships among use cases.

Use cases should represent meaningful user goals, rather than individual buttons, screens, or minor actions.

Section 5. Data Requirements

This section specifies the major data that the system is expected to capture, store, process, and retrieve.

5.1 Major Data Entities

Identify and briefly describe the major data entities required by the system. Examples:

User· Application· Transaction· Document· Evaluation· Notification

5.2 Entity-Relationship Diagram / Data Model

Provide an ERD or other appropriate data model showing:

  • entities;
  • major attributes;
  • relationships; and
  • cardinalities.
Remember — The data model should support the functional requirements identified in the SRS.

5.3 Data Dictionary

Define the important data elements required by the system. Example:

Data ElementDescriptionData TypeRequiredConstraints
user_idUnique identifier of a userIntegerYesPrimary key
emailUser email addressStringYesMust be unique
submission_dateDate and time of submissionDate/TimeYesSystem generated
Right-size the detail — The level of detail should be appropriate to the complexity of the proposed system.

Section 6. Interface Requirements

This section specifies how users and external systems are expected to interact with the proposed system.

6.1 User Interface Requirements

Describe important requirements governing the user interface. These may include:

  • major screens or interface components;
  • navigation;
  • form behavior;
  • validation and feedback;
  • responsive behavior;
  • accessibility considerations; and
  • error and confirmation messages.

Wireframes and mockups

Wireframes or mockups should be included where appropriate to illustrate the intended user interface. These represent the proposed interface and should be consistent with the functional requirements and use cases.

6.2 External System/Software Interfaces

Identify required interfaces with external systems or services, where applicable. For each interface, describe:

Describe…Example interfaces
External system or serviceAuthentication services
Purpose of the integrationAPIs
Information exchangedEmail services
Relevant interface or communication methodPayment services
Existing institutional systems

6.3 Other Interfaces

Describe hardware, network, communication, or other interfaces only when relevant to the proposed system.

Section 7. Non-Functional Requirements

This section specifies how well the system is expected to operate and identifies relevant quality and operational requirements.

What vs. how well

Functional Requirements
  • Specify what the system must do.
Non-Functional Requirements
  • Specify qualities, constraints, or performance expectations — how well the system operates.

Only include categories applicable to the proposed system.

7.1 Security and Privacy

Specify relevant requirements concerning:

  • authentication;
  • authorization and access control;
  • protection of sensitive information;
  • audit logging;
  • session management; and
  • data privacy and protection.

7.2 Performance

Specify relevant requirements concerning:

  • expected response time;
  • transaction processing;
  • expected number of users; and
  • workload or capacity.

7.3 Usability and Accessibility

Specify relevant requirements concerning:

  • consistency of navigation;
  • error prevention and recovery;
  • accessibility;
  • responsive interfaces; and
  • user feedback.

7.4 Reliability and Availability

Specify relevant requirements concerning:

  • expected system availability;
  • backup and recovery;
  • handling of failures; and
  • protection against data loss.

7.5 Other Quality Requirements

Specify other relevant requirements such as:

Maintainability· Compatibility· Portability· Scalability
Relevance over completeness. Do not include a quality category merely for completeness. Non-functional requirements should be relevant to the proposed system and specific and verifiable whenever possible.
10 · The Nine Sections

Section 8. Business Rules

This section identifies organizational rules, policies, or conditions that govern the processes supported by the system.

Business Rules (BRs) describe rules originating from the organization or operational context, rather than the behavior of the software itself. Each business rule should have a unique identifier. Examples:

BR-001 — An applicant may have only one active application per application cycle.
BR-002 — Applications submitted after the official deadline shall not be accepted.
BR-003 — Only users assigned the Approver role may approve an application.

From business rule to functional requirement

Business rules may give rise to one or more functional requirements. For example:

Rule → Requirement

Business Rule
  • BR-002: Applications submitted after the official deadline shall not be accepted.
Corresponding Functional Requirement
  • FR-027: The system shall prevent submission of applications after the configured application deadline.
Why the distinction matters — It helps establish why a particular system behavior is required.

Section 9. Requirements Traceability Matrix

The Requirements Traceability Matrix (RTM) establishes the relationship among the identified requirements and the analysis from which they were derived.

It provides a basis for determining whether the system, once developed, satisfies the requirements established in the System Blueprint. Suggested format:

Requirement IDRequirementSource/BasisRelated Use CaseModule/FeatureAcceptance Criterion
FR-001The system shall authenticate registered usersStakeholder requirementUC-01AuthenticationValid registered users can successfully authenticate
FR-005The system shall allow users to submit applicationsProcess analysisUC-03ApplicationA complete application can be submitted and recorded
NFR-003The system shall enforce role-based accessSecurity requirementMultipleAccess ControlUsers can access only functions permitted for their assigned roles

Source/Basis

The Source/Basis should identify where the requirement originated, such as:

Stakeholder interview· Survey or needs assessment· Process analysis· Document or policy analysis· Observation· Legal or regulatory requirement

Acceptance Criterion

Acceptance Criterion — Should state the condition that would indicate that the requirement has been satisfactorily implemented.
12 · Wrap-up

Key Takeaways

  1. The SRS is the requirements baseline. It guides system design, development, testing, and evaluation, so every requirement must be clear, specific, consistent, feasible, and verifiable.
  2. Sections 1–2 set context, not discussion. Give only enough overview, scope, and environment to understand the requirements — don't repeat the manuscript.
  3. Functional requirements are the core. Uniquely numbered, written as "The system shall…", organized by module, and testable — never "user-friendly."
  4. FRs and use cases are different. FRs say what the system must do; use cases say how an actor reaches a goal. One use case may map to several FRs.
  5. Use cases are user goals, not buttons, screens, or messages. Specify major use cases in detail and link them to their FRs.
  6. The data model supports the FRs. Entities, ERD, and data dictionary are sized to the system's complexity.
  7. Interfaces stay consistent. Wireframes and mockups must match the FRs and use cases; external interfaces state purpose, data exchanged, and method.
  8. NFRs are relevant and verifiable. Include a quality category only when it applies to the system.
  9. Business rules explain why. Rules come from the organization and give rise to the FRs that enforce them.
  10. The RTM closes the loop. Each requirement traces to its source, use case, and module, with an acceptance criterion for judging the developed system.
